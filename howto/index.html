Runbook

คู่มือระบบ Star Content Ops

คู่มือปฏิบัติงานที่ตรงกับโค้ดที่ติดตั้งจริง ไม่มีฟีเจอร์ที่ยังไม่ได้ทำ ทุกคำสั่งและทุกเส้นทาง API ในหน้านี้อ่านได้จาก star_api.py และโมดูล star_automation.py

01 เริ่มต้นใช้งาน

ครั้งแรกใช้เวลาประมาณ 15 นาที
rocket_launch
ลำดับที่แนะนำ

ตั้งค่าผู้ให้บริการให้ครบก่อน แล้วรันโหมดซ้อมหนึ่งรอบเพื่อดูว่าติดเงื่อนไขอะไรบ้าง ค่อยเปิดโหมดจริง และเปิดตารางเวลาเป็นขั้นสุดท้าย

  1. เข้าสู่ระบบผ่าน Basic Auth ของ nginx

    ทั้งไซต์อยู่หลัง Basic Auth อยู่แล้ว API ทำงานที่ 127.0.0.1:9001 และรับเฉพาะคำขอจากต้นทางเดียวกันเท่านั้น

  2. ล็อกอิน Claude CLI บนเซิร์ฟเวอร์

    รัน claude login ในบัญชีผู้ใช้ที่รันเซอร์วิส ขั้นตอนนี้ทำผ่านหน้าเว็บไม่ได้โดยตั้งใจ

  3. ตั้งค่าผู้ให้บริการที่เหลือในศูนย์ควบคุม

    เปิด ศูนย์ควบคุม › การเชื่อมต่อผู้ให้บริการ แล้วกรอกค่าที่ต้องใช้ตามหัวข้อถัดไป

  4. รันโหมดซ้อมหนึ่งวัน

    เลือกวันที่วันเดียว วันเกิดครบ 7 วัน ขั้นตอน astro → script → audio → video และเปิดโหมดซ้อมไว้ ผลลัพธ์จะบอกว่าขาดเงื่อนไขอะไร

  5. ปิดโหมดซ้อมเมื่อไม่มีเงื่อนไขค้าง

    งานจริงจะเขียนไฟล์ลงในโปรเจกต์และมีค่าใช้จ่ายตามผู้ให้บริการที่ใช้

02 การตั้งค่าผู้ให้บริการ

8 รายการ

ค่าลับทุกชิ้นถูกเขียนลงไดเรกทอรีสถานะด้วยสิทธิ์ 0600 (ไดเรกทอรีเป็น 0700) และ API จะไม่ส่งค่ากลับมาแสดงไม่ว่ากรณีใด ถ้าต้องการเปลี่ยนค่า ให้กรอกค่าใหม่ทับ ระบบไม่มีทางอ่านค่าเดิมมาเติมให้

Claude CLI

อัตโนมัติ

ใช้เขียนบทภาษาไทย ยืนยันตัวตนด้วยการล็อกอิน CLI บนเซิร์ฟเวอร์

  • รัน claude login ในบัญชีผู้ใช้ที่รันเซอร์วิส
  • ตั้ง CLAUDE_CONFIG_DIR ถ้า home ของผู้ใช้เขียนไม่ได้
  • ใช้สิทธิ์แบบ subscription ไม่ใช่ API key รายครั้ง

ระบบนี้ ไม่รับ session token ของ Claude ผ่านเบราว์เซอร์ การกดปุ่ม "ทดสอบ" จะสั่ง claude auth status พร้อมกำหนดเวลาสูงสุด 20 วินาที

Google Cloud TTS

อัตโนมัติ

ใช้สังเคราะห์เสียงพากย์ภาษาไทย

  • เปิดใช้งาน Cloud Text-to-Speech API ในโปรเจกต์ Google Cloud
  • สร้าง service account key แล้ววาง JSON ทั้งก้อนลงในฟอร์ม
  • หรือระบุ path ของไฟล์ที่อัปโหลดไว้แล้ว โดยต้องอยู่ในไดเรกทอรีสถานะเท่านั้น

การกด "ทดสอบ" ตรวจเฉพาะโครงสร้าง JSON แบบออฟไลน์ ส่วน "ทดสอบจริง" จะเรียก ListVoices ซึ่งเป็นคำสั่งอ่านข้อมูลที่ไม่มีค่าใช้จ่าย และไม่มีการสังเคราะห์เสียงระหว่างทดสอบ

ถ้าไม่ได้ตั้งค่าไว้ ระบบจะใช้ gTTS เป็นทางเลือกฟรีที่คุณภาพต่ำกว่า

YouTube

อัตโนมัติ

อัปโหลดวิดีโอผ่าน YouTube Data API v3

  • เปิดใช้งาน YouTube Data API v3 และตั้งค่า OAuth consent screen
  • ขอบเขตที่ใช้คือ youtube.upload
  • วาง OAuth client JSON แล้วกด "เชื่อมต่อบัญชี" เพื่อเริ่ม OAuth
  • ต้องลงทะเบียน Redirect URI ที่หน้าการ์ดแสดงไว้ใน Google Cloud ก่อน

ระบบใช้ PKCE และ state แบบใช้ครั้งเดียวอายุ 10 นาที วิดีโอที่อัปโหลดถูกตั้งเป็น private เสมอ โควตาอัปโหลดของ API อยู่ที่ประมาณ 6 คลิปต่อวันต่อโปรเจกต์

Facebook Page

อัตโนมัติ

โพสต์วิดีโอขึ้นเพจผ่าน Graph API

  • ต้องเป็นผู้ดูแลเพจนั้น
  • ใช้ Page access token แบบ long-lived พร้อมสิทธิ์ pages_manage_posts และ pages_read_engagement
  • เพจที่ไม่ได้เป็นเจ้าของต้องผ่าน App Review ก่อน

"ทดสอบจริง" จะเรียก /me?fields=id,name เท่านั้น

LINE Messaging API

อัตโนมัติ

ส่งข้อความและวิดีโอแบบ broadcast หรือ push

  • ต้องมี LINE Official Account ที่เปิด Messaging API
  • ใช้ channel access token แบบ long-lived
  • ข้อความ broadcast กินโควตารายเดือนของแพ็กเกจ

LINE ต้องการ URL ของสื่อที่เข้าถึงได้จากภายนอก จึงต้องตั้งค่า Cloudflare R2 และเลือก R2 เป็นปลายทางด้วย มิฉะนั้นงานจะหยุดที่สถานะ "ติดเงื่อนไข"

Cloudflare R2

อัตโนมัติ

ที่เก็บสื่อสาธารณะ และเป็นต้นทาง URL ให้ LINE

  • ต้องมี bucket และ API token แบบ S3 ที่อ่านเขียนได้
  • ต้องระบุ public base URL (custom domain หรือ r2.dev)

ไฟล์ถูกอัปโหลดไปที่ star/<วันที่>/<วันเกิด>.mp4 "ทดสอบจริง" จะเรียก HeadBucket เท่านั้น

TikTok

กึ่งอัตโนมัติ

Content Posting API ต้องผ่านการอนุมัติแอปนักพัฒนา แอปที่ยังไม่ผ่านการตรวจสอบโพสต์ได้เฉพาะแบบส่วนตัวหรือแบบร่างเท่านั้น

ระบบนี้จึงไม่อัปโหลดขึ้น TikTok ให้ แต่จะเตรียมชุดไฟล์สำหรับอัปโหลดเองไว้ที่ output/<วันที่>/handoff/tiktok/ และจะไม่รายงานว่าเผยแพร่สำเร็จ

Shopee

ทำเอง

Shopee ไม่มี API สาธารณะสำหรับเผยแพร่วิดีโอคอนเทนต์แบบ affiliate จึงต้องอัปโหลดเองใน Shopee Video / Affiliate ทุกครั้ง

ระบบเตรียมไฟล์และแคปชั่นไว้ที่ output/<วันที่>/handoff/shopee/ เท่านั้น

04 โหมดซ้อมกับโหมดจริง

dry_run
ความแตกต่างระหว่างโหมดซ้อมและโหมดจริง
หัวข้อ โหมดซ้อม โหมดจริง
เรียกผู้ให้บริการ ไม่มีเลย มี ตามขั้นตอนที่เลือก
เขียนไฟล์ลงโปรเจกต์ ไม่เขียน เขียนแบบ atomic เมื่อขั้นตอนนั้นสำเร็จ
ค่าใช้จ่าย ไม่มี ตามผู้ให้บริการที่ใช้ (TTS คิดตามอักขระ, แพลตฟอร์มคิดตามโควตา)
เงื่อนไขที่ขาด รายงานไว้ในผลลัพธ์ แต่ยังถือว่างานสำเร็จ งานหยุดทันทีด้วยสถานะ "ติดเงื่อนไข"
สิ่งที่ได้กลับมา รายการคำสั่งที่จะรันและไฟล์ที่จะสร้าง ผลลัพธ์จริงของแต่ละขั้นตอนและรายการไฟล์ที่สร้าง
verified_user
โหมดซ้อมเป็นขอบเขตจริง ไม่ใช่แค่ธง

ในโหมดซ้อม โค้ดส่วน execute() ของแต่ละขั้นตอนไม่ถูกเรียกเลย ระบบเรียกเฉพาะ plan() ซึ่งเป็นฟังก์ชันที่ไม่มีผลข้างเคียง จึงไม่มีทางที่การซ้อมจะเผลอเรียกผู้ให้บริการได้

05 ตารางเวลาอัตโนมัติ

Asia/Bangkok
  • ตารางเวลามีได้ชุดเดียว ทำงานวันละหนึ่งครั้งตามเวลากรุงเทพฯ
  • ค่าเริ่มต้นคือปิดใช้งาน และค่าเริ่มต้นของ dry run คือเปิด
  • ป้องกันการรันซ้ำในวันเดียวกันด้วยคีย์หลักของตารางในฐานข้อมูล ไม่ใช่แค่การเช็คในหน่วยความจำ
  • ถ้าถึงเวลาแล้วมีงานอื่นทำงานอยู่ ระบบจะข้ามรอบนั้น ไม่ต่อคิวสะสม
  • ไม่มีการลองใหม่อัตโนมัติ งานที่ล้มเหลวต้องสั่งทำใหม่ด้วยตนเอง
  • ตั้ง "วันที่เป้าหมาย" ให้เลื่อนไปข้างหน้าได้ เพื่อผลิตล่วงหน้า

06 ข้อจำกัดการเผยแพร่

อ่านก่อนเปิดโหมดจริง
front_hand
ระบบจะไม่อ้างว่าเผยแพร่สำเร็จถ้าไม่ได้เผยแพร่จริง

ปลายทางที่ทำอัตโนมัติไม่ได้จะได้ผลลัพธ์เป็น manual_handoff พร้อม published: false เสมอ หน้าเว็บแสดงค่านี้ตามที่ API ส่งกลับมาโดยไม่ตีความใหม่

  • YouTube — อัปโหลดเป็น private เสมอ ต้องเปลี่ยนเป็นสาธารณะเอง โควตา API จำกัดที่ประมาณ 6 คลิปต่อวันต่อโปรเจกต์
  • Facebook — โพสต์ผ่าน Page video API ความสามารถขึ้นกับสิทธิ์ของโทเคนและสถานะ App Review
  • LINE — ต้องมี URL สาธารณะของสื่อ จึงต้องเปิดใช้ R2 คู่กันเสมอ และ broadcast กินโควตารายเดือน
  • R2 — อัปโหลดไฟล์อย่างเดียว ไม่ได้ทำ CDN invalidation ให้
  • TikTok — ต้องอัปโหลดเอง จนกว่าแอปนักพัฒนาจะผ่านการอนุมัติ
  • Shopee — ต้องอัปโหลดเองเสมอ ไม่มี API สาธารณะรองรับ

07 การแก้ปัญหา

อาการที่พบบ่อย
อาการ สาเหตุ และวิธีแก้
อาการ สาเหตุที่เป็นไปได้ วิธีแก้
งานขึ้นสถานะ "ติดเงื่อนไข" ขาดค่าตั้งค่าของผู้ให้บริการ หรือขาดไฟล์จากขั้นตอนก่อนหน้า อ่านข้อความในช่อง safe_error ซึ่งระบุเงื่อนไขที่ขาดไว้ตรง ๆ แล้วแก้ตามนั้น
สั่งงานแล้วได้ HTTP 409 มีงานอยู่ในคิวหรือกำลังทำงาน ยกเลิกงานเดิมก่อน หรือรอให้จบ ระบบจงใจให้รันได้ครั้งละหนึ่งงาน
งานค้างสถานะ "กำลังทำงาน" หลังรีสตาร์ต เซอร์วิสถูกรีสตาร์ตระหว่างงานกำลังรัน ระบบทำเครื่องหมายเป็นล้มเหลวให้อัตโนมัติตอนเริ่มเซอร์วิส แล้วสั่งทำใหม่ด้วยตนเอง
"ทดสอบจริง" ตอบว่าปิดการเชื่อมต่อ เซอร์วิสรันด้วย STAR_DISABLE_NETWORK=1 ตัวแปรนี้ใช้ในชุดทดสอบ ให้ถอดออกจาก environment ของเซอร์วิสจริง
ขั้นตอน astro ล้มเหลวทันที ยังไม่ได้ติดตั้งโมดูล swisseph ติดตั้ง pyswisseph ในสภาพแวดล้อมที่เซอร์วิสใช้
ขั้นตอน video ล้มเหลว ไม่มี ffmpeg หรือไม่มีฟอนต์ไทยบนเครื่อง ติดตั้ง ffmpeg และ fonts-noto-core หรือ fonts-thai-tlwg
หน้าเว็บเตือนเรื่องสิทธิ์ไฟล์ ไฟล์ในไดเรกทอรีสถานะถูกแก้สิทธิ์ให้กว้างกว่าเจ้าของ แก้กลับเป็น chmod 600 สำหรับไฟล์ และ chmod 700 สำหรับไดเรกทอรี
กดปุ่มแล้วได้ HTTP 403 คำขอไม่มีเฮดเดอร์ยืนยันเจตนา หรือมาจากต้นทางอื่น ใช้งานผ่านหน้าเว็บนี้เท่านั้น สคริปต์ภายนอกต้องส่ง X-Star-Intent: automation-control ด้วย

08 ความปลอดภัย

ที่บังคับใช้จริงในโค้ด
  • ต้นทางเดียวกันเท่านั้น — คำขอที่มีเฮดเดอร์ Origin ต่างจาก Host จะถูกปฏิเสธด้วย 403
  • เฮดเดอร์ยืนยันเจตนา — ทุกเส้นทางที่เปลี่ยนสถานะต้องส่ง X-Star-Intent: automation-control ซึ่งฟอร์มข้ามโดเมนส่งไม่ได้
  • ข้อยกเว้นที่ตั้งใจ — หน้า callback ของ OAuth ไม่ต้องใช้เฮดเดอร์นี้ เพราะเป็นการเปลี่ยนหน้าจาก Google โดยตรง จึงใช้ค่า state แบบเดาไม่ได้ ใช้ครั้งเดียว และหมดอายุใน 10 นาที เป็นเกราะแทน
  • ไม่มี shell — ทุกคำสั่งภายนอกเรียกด้วย argv list ไม่มี shell=True อยู่ในโค้ดฝั่งเซิร์ฟเวอร์เลย และมีเทสต์ตรวจข้อนี้
  • ไม่มีพาธที่ผู้ใช้กำหนด — ไฟล์ credential ตั้งชื่อโดยระบบเท่านั้น และพาธของไฟล์ key ต้องอยู่ในไดเรกทอรีสถานะ
  • การกรองค่าลับ — ทุกข้อความที่เข้าสู่บันทึกงาน ผลลัพธ์ และคำตอบของ API ผ่านตัวกรองกลางที่ปิดบังโทเคน คีย์ และบล็อก private key
  • ขอบเขตที่จำกัดไว้ — ขนาด body, จำนวนพารามิเตอร์, จำนวนงานและบันทึกที่คืนกลับ, เวลาสูงสุดของแต่ละขั้นตอน, ช่วงวันที่ และจำนวนงานพร้อมกัน ถูกจำกัดทั้งหมด
  • ไดเรกทอรีสถานะ — กำหนดด้วย STAR_STATE_DIR ค่าเริ่มต้นบนเครื่องจริงคือ /var/lib/star ไดเรกทอรีเป็น 0700 และไฟล์เป็น 0600

สิ่งที่ระบบนี้ตั้งใจไม่ทำ

ไม่มี endpoint สำหรับรันคำสั่งใด ๆ ตามใจผู้ใช้ ไม่รับ session token ของ Claude ผ่านเบราว์เซอร์ ไม่ส่งค่าลับกลับมาแสดงในหน้าเว็บ และไม่ลองงานใหม่เองโดยอัตโนมัติ
